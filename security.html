Security & architecture

Your documents stay yours. Your SharePoint stays closed.

External signers never touch your tenant. A short-lived, encrypted signing bridge verifies them, stamps the document, and hands it back.

Review the permissions IT verification checklist

Two-tier architecture

Why there's a bridge — and why it's safe.

SharePoint Online doesn't let anonymous outsiders view a contract and write a signed copy into a private library without either a guest account or a risky anonymous write link. The signing bridge removes both.

Tier 1 · Inside Microsoft 365

Your SharePoint tenant

  • Staff send and track from the web part
  • Tracking lists, hashes and audit logs live here
  • Originals and signed copies are stored here, permanently
⇄

Tier 2 · Signing bridge

Encrypted, auto-deleting courier

  • AES-256-GCM encrypted while out for signature
  • Holds zero SharePoint or Microsoft Graph permissions
  • Originals deleted on confirmed save-back; signed copies after 7 days; declined/expired within the hour; remaining records after 90 days
⇄

Outside

External signer

  • Single-use link + 6-digit email code
  • No Microsoft login, no SharePoint access
  • Sees the document only after verification

Protections

Defence in depth, end to end.

Nothing stored in plaintext

Documents and signer details are encrypted with AES-256-GCM, each record bound to its envelope. Without the separately held key, the store is unreadable — and the bridge refuses to start unencrypted.

Links that can't be guessed or replayed

256-bit single-use links are stored only as SHA-256 hashes — even in your SharePoint lists. After signing, declining or revoking, a link is permanently dead (410 Gone).

Brute-force lockout

Five wrong codes lock the challenge, with a 30-second resend cooldown. A forwarded link alone reveals neither the contract nor the other parties.

Tenant-isolated, keyless API

Every call from the web part carries the user's Microsoft Entra token. The bridge checks signature, audience, issuer, tenant and scope, accepts only onboarded tenants, and has no shared API keys.

Fail-closed by design

If stamping or saving fails, nothing is marked signed. The failure is recorded, surfaced on the dashboard, and retried — and the saved file must match its SHA-256 hash.

Hardened transport & logs

HTTPS with HSTS, no-referrer and anti-framing headers, a strict CORS allowlist, and logs that never contain signing links, codes or document contents.

For SharePoint administrators

Four delegated permissions. Nothing more.

Every permission runs as the signed-in user — Send & Sign can never see a site or mailbox that user can't already access.

PermissionWhy it's neededWhat it can't do
Microsoft Graph · User.ReadReads the sender's name, title and email for invitations and the audit trail.Can't read other users' data or directory objects.
Microsoft Graph · Mail.SendSends invitations and reminders from the sender's own mailbox, so clients trust them.Can't read any inbox or send without a user action.
Microsoft Graph · Sites.Read.AllRead-only browsing of sites, libraries and folders the user can already see in SharePoint.Can't write, overwrite or delete anything via Graph, or bypass SharePoint permissions.
esign-api · Envelope.ReadWriteAuthenticates the web part to the signing bridge — no stored secrets or API keys.Grants no SharePoint or Graph access; works only on your own tenant's envelopes.

$0 per API call

Everything used is standard Microsoft 365 API, included in your licences. No metered APIs.

Can't crash SharePoint

Pure client-side SPFx — no server-side code, no farm solutions, no changes to the host page.

Originals untouched

Signed output is always a separate copy. Only PDFs and interactive HTML proposals are accepted.

Zero-impact removal

Remove the app and it stops instantly. Every file, list and audit ledger stays in SharePoint.

Package transparency

Don't take our word for it. Unzip it.

A .sppkg is a standard ZIP archive built with Microsoft's official SPFx toolchain. Rename it to .zip and inspect every file before you upload.

  • App manifest declaring exactly the four permissions above
  • The web part registration and its compiled React bundle
  • Localised labels, icons and open-source licence notices

What's not inside

  • No server-side executables, DLLs or farm solutions
  • No external runtime script downloads — compliant with SharePoint's 2026 Content Security Policy
  • No embedded secrets, API keys or passwords
  • No telemetry trackers or third-party analytics

Every release passes a GPL/AGPL licence gate, secret scanning and a CycloneDX software bill of materials.

5-minute IT verification

Verify it yourself before rollout.

1

Inspect the archive

2

Scan it

3

Review API access

Check the pending requests in SharePoint Admin Center → Advanced → API access before approving.

4

Pilot on one site

Add the web part to a dedicated test site and confirm the lists and archive folder are created there only.
